# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core. With `DATABASE_URL` set it uses Postgres (on this machine, local Postgres in Docker, not Supabase) in the `undercover` schema, with at most 4 connections; without it, SQLite, which the tests use. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount, and refuses any amount over the approval limit with a 403. A handler's sign-off pays the claim in the backend itself. Every route but `GET /api/health` needs the agent's key (`UNDERCOVER_API_KEY` in an `X-API-Key` header, compared with `secrets.compare_digest`), a signed-in handler, or, for the reads both use, either; the checks read the headers themselves, so no operation has a key or token input. `GET /api/agent/openapi.json` is an OpenAPI document of the claim agent's six operations only (`get_claim`, `get_policy`, `get_claim_history`, `calculate_payout`, `record_decision`, `pay_claim`), for the AgentCore Gateway. The payout rules are `backend/payout.py`, behind `calculate_payout` (`POST /api/claims/{claim_id}/payout`), with each plan from the `plans` table. Seeding loads the plans from `context/plans.yaml` and the policy wording and the claims manual, with their versions, from `context/` into the `documents` table; the app reads `context/` only while seeding. `record_decision` checks each record against claims manual section 14, and an approval against the claim's latest calculation. `hold_for_sign_off` (the key only, not in the agent's document) holds an approved claim for sign-off when the Gateway refused its payment. The backend keeps the settings, the claim agent's configuration and the improver's recipe in versions (diffs from Python's `difflib`), and the rounds; it applies the rule that keeps or rolls back a version (`backend/rule.py`).
- `backend/auth.py`: checks a Supabase Auth access token on every handler action with PyJWT's `PyJWKClient`, against the public keys at `{VITE_SUPABASE_URL}/auth/v1/.well-known/jwks.json` with the audience `authenticated`, and finds the handler by the token's email. No Supabase secret is needed. On this machine Supabase Auth is Supabase's local stack, with no Supabase account. With `AUTH_JWKS_URL`, `AUTH_ISSUER` and `AUTH_AUDIENCE` set it checks those instead: on AWS, an Amazon Cognito user pool's keys, its issuer, and the app client's id, which only Cognito's ID tokens carry.
- `backend/judge.py`: the judge, Jev (`typesafe/jev-1.13`), through OpenRouter's Decisions endpoint with the `openrouter` package. It grades an evaluation's claims in parallel as it finishes, each call with a 10-second timeout and retries off, at the address in `JUDGE_URL`.
- `context/`: the context layer, an MCP server (FastMCP from the `mcp` package, stateless, JSON responses) that serves data governance's seven files as read-only tools: `lookup_term`, `describe_fields`, `get_plan`, `get_claim_rules`, `search_reference_data`, `search_documents`, `list_sections` and `read_section`. It reads the files once when it starts, splits each document at its numbered headings, and names each answer's file with its system, owner and review date. `uv run -m context` serves it at `http://127.0.0.1:8006/mcp`.
- `agent/`: the claim agent on OpenRouter, a hand-written LangGraph graph whose first node, `check`, reads the claim on a second model (`openai/gpt-6-luna` at reasoning effort `none`, or `MODEL_NAME`) with Structured Outputs and refers a claim that tries to instruct its handler; then the model and its tools, a wait for a handler's sign-off with `interrupt()`, and a payment step for a claim within the limit. Its model's tools take no ids: they read the claim, its policy and its customer from LangGraph's run context. The tools and the graph's payment reach the app and the context layer by one of two routes, picked when a claim graph is built: `agent/gateway.py`, the AgentCore Gateway at `UNDERCOVER_GATEWAY_URL` as MCP tools named `undercover-app___<operation>` and `undercover-context___<tool>`, signed with SigV4 for `bedrock-agentcore` with the AWS CLI's credentials and region; or `agent/direct.py`, the app with the key and the context layer at `UNDERCOVER_CONTEXT` (default `http://127.0.0.1:8006/mcp`) unsigned. Both use the `mcp` package's `ClientSession` over streamable HTTP, a session for each call on an event loop of its own (`agent/mcp_client.py`). With `UNDERCOVER_MEMORY_ID` set, the graph's store is AgentCore Memory (`AgentCoreMemoryStore` from `langgraph-checkpoint-aws`, `agent/memory.py`): a `remember` node saves each decided claim as two events, and the model gets `search_memory`, kept to the claim's customer; evaluations work without it. Every other request to the backend (the bookkeeping, the check's read and referral, the runs) goes through `backend()` in `agent/main.py`, which sends the key, to `UNDERCOVER_API` (default `http://127.0.0.1:8000`). It saves its progress after every step with LangGraph's synchronous `PostgresSaver` in the same database, a saver of its own for each claim run on the process's shared pool of 4 connections, with prepared statements off (`prepare_threshold=None`) so it works through either of Supabase's poolers. It records each model call's tokens and cost, from OpenRouter's `usage.cost`, and its working time. Each claim is traced in Langfuse, in a session named after its thread and tagged with its run.
- `agent/dispatcher.py`: the dispatcher, a LangGraph graph with no model. It lists a run's claims and fans out with one `Send` per claim, with `max_concurrency` set to N, through `work()` in `agent/main.py`, the only place it touches the claim agent. It works dispatches and evaluations alike, and a round's evaluations.
- `agent/entrypoint.py`: the agent as an AgentCore app, `BedrockAgentCoreApp` from `bedrock-agentcore` (a Starlette app), with one entrypoint at `/invocations` that takes a JSON payload naming an operation (`work_run`, `work_round`, `carry_round_on`, `resume_claim`, `health`) and its inputs, checked with Pydantic, and its own `/ping`. Each operation answers at once, `{"accepted": true}` or `{"refused": "<reason>"}`, and works on a thread registered with `app.add_async_task`, so the ping says `HealthyBusy` while it works. Nothing happens at import; it gets ready on its first request, once per process. Off AgentCore Runtime every operation but `health` needs `Authorization: Bearer <UNDERCOVER_API_KEY>`; on Runtime (any `AGENTCORE_CREDENTIAL_<NAME>_NAME` set) AWS checks the caller, and the agent fetches its credentials from AgentCore Identity (`requires_api_key`) into the settings they name. `npm run dev` serves it with uvicorn on 127.0.0.1:8080 (`UNDERCOVER_AGENT`), and the platform team's `runtime/main.py` runs it with `app.run()`. The backend keeps one dispatch, evaluation or working round going at a time, in a one-row table, `agent_work`, taken with one conditional update (free, or quiet for five minutes, when the work it held is marked stopped with "The agent stopped answering"); it creates the run or the round, or records a handler's review, and commits before it calls the agent, through `backend/agent_service.py`, to work that run or round by its id (`work_run`, `work_round`, or `carry_round_on` after a review), undoing its part when the agent didn't take it, and after each sign-off (`resume_claim`, which never touches the slot). The agent keeps no lock of its own, tells the backend every minute while it works a run or a round (`record_work_heard`), and stops only its own run or round when that work fails. The backend calls it over HTTP with the key and a 10-second timeout, or, with `UNDERCOVER_AGENT_RUNTIME` set to the runtime's ARN, with boto3's `invoke_agent_runtime` (a new session each call, one attempt, 5 seconds to connect and 20 to read). The agent reaches claims, documents and its instructions only through the backend's API. It builds each run's claim agents from the configuration version the run uses (version 1 is `openai/gpt-6-luna` at low reasoning effort), or from the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, at its default effort.
- `agent/improver.py`: the improver, a LangChain `create_agent` on `openai/gpt-6-luna` at medium effort (or `MODEL_NAME`), with parallel tool calls off, at most 30 model calls a stretch of work, and `HumanInTheLoopMiddleware` on its two propose tools, saved by a `PostgresSaver` of its own. It reaches the backend only through `agent/improver_api.py`. Its work in a round is one Langfuse session, `Round <id>`.
- `dashboard/`: React, Vite and TypeScript. Handlers sign in with `@supabase/supabase-js` (`signInWithPassword`, from `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`), and each action sends the session's access token. A build with `VITE_COGNITO_USER_POOL_ID` and `VITE_COGNITO_CLIENT_ID` signs in through Cognito instead (`InitiateAuth` with `USER_PASSWORD_AUTH` by `fetch`, no SDK) and sends the ID token; `dashboard/src/auth.ts` chooses. The round's chart is SVG, with no chart library.
- `e2e/`: Playwright tests, with stand-ins for the agent's AgentCore app, Supabase Auth and the judge.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`, with a `server` group for the app's package (`boto3` among it, for calling the agent on Runtime), a `context` group (`mcp`, `pyyaml`, `mangum`) for the context layer's, and a `runtime` group with exactly what the agent needs on AgentCore Runtime, `bedrock-agentcore` included. Node 26. The OpenRouter key is `OPENROUTER_API_KEY` in `.env`, beside the agent's `UNDERCOVER_API_KEY`, the Langfuse keys, `DATABASE_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` and `HANDLER_PASSWORD`.

## Deployment

- `npm run build` builds the dashboard into `dashboard/dist` (git-ignored), with `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` built in, read from `.env` when there is one and otherwise from the shell. Only `npm run dev` and `npm run build` read `.env`; Vitest and the end-to-end dashboard don't.
- When `dashboard/dist` exists, the backend serves it at `/` after every route: a file gets itself, any other path outside `/api/` gets `index.html`, and an unknown `/api/` path gets FastAPI's JSON 404. Without it, nothing is mounted.
- The package holds `backend/` (without its tests), `data/`, `dashboard/dist/` and the `server` dependency group's packages from `pyproject.toml`, installed as Linux wheels for Python 3.12. The `server` group lists what the backend imports; `npm run check:server` imports `backend.main` with only that group, in a temporary environment that leaves `.venv` as it is. The backend imports nothing from `agent/`, reads files only from the package and writes none.
- The context layer's package is `context/` without its tests, with the `context` group's packages installed for Linux and Python 3.12. Its Lambda handler is `context.server.handler`, which builds a fresh server for each request (FastMCP's session manager runs once, and Mangum runs the app's startup and shutdown around every request), with FastMCP's Host check off, behind a Function URL with `AWS_IAM` auth, with no environment variables. `npm run check:context` imports `context.server` with only that group, in a temporary environment.
- The app's package needs no `context/`: the manual's version for a decision comes from the documents table.
- The agent's package for AgentCore Runtime is `runtime/` (the platform team's `runtime/main.py`, which runs the app from `agent/entrypoint.py`) with `agent/` beside it, without the tests, and the `runtime` group's packages at `uv.lock`'s versions. `npm run check:runtime` imports `runtime.main` with only that group, in a temporary environment.
- The AgentCore project in `agentcore/` deploys one runtime, `agent`, with `agentcore deploy`, built for Linux on ARM and Python 3.12. Runtime starts `runtime/main.py` in each session. The runtime's role may call the Gateway and use the Memory (`runtime/policy.json`). Its credentials in AgentCore Identity are `OPENROUTER_API_KEY`, `UNDERCOVER_API_KEY` and `DATABASE_URL`, which the agent fetches on its first request; `UNDERCOVER_API`, `UNDERCOVER_GATEWAY_URL` and `UNDERCOVER_MEMORY_ID` come from `agentcore/.env.local` when `agentcore deploy` runs. On Runtime the agent's tools always go through the Gateway, and the runtime's own role signs its requests to the Gateway and the Memory.
- UnderCover's own route on AWS keeps its data in AWS: `DATABASE_URL` for the app on Lambda and for the agent on Runtime is the database on Amazon RDS for PostgreSQL, straight to port 5432 with TLS (RDS has no transaction pooler; prepared statements are off on both), and handlers sign in through Amazon Cognito (`AUTH_JWKS_URL`, `AUTH_ISSUER`, `AUTH_AUDIENCE`, and the dashboard built with `VITE_COGNITO_USER_POOL_ID` and `VITE_COGNITO_CLIENT_ID`). `labs/week3/week3_aws_route.py` holds the labs' code for it. People sign in to AWS through IAM Identity Center, never an IAM user.
- The app's setting `UNDERCOVER_AGENT_RUNTIME` is the agent runtime's ARN; the app's role needs `bedrock-agentcore:InvokeAgentRuntime` on it.
- The agent's settings: `UNDERCOVER_GATEWAY_URL` (the Gateway, when set), `UNDERCOVER_CONTEXT` (the context layer on the direct route), `UNDERCOVER_MEMORY_ID` (the memory, when set), `UNDERCOVER_API` (the app), and the AWS credentials and region from the AWS CLI's configuration whenever `UNDERCOVER_GATEWAY_URL` or `UNDERCOVER_MEMORY_ID` is set. The agent reads them when it builds a claim graph, not when it is imported.
- On AWS Lambda the handler is `backend.main.handler`, `Mangum(app, lifespan="off")`. On a web server the app is `backend.main:app`, as in `uv run -m uvicorn backend.main:app`.
- The function's environment is `DATABASE_URL` (Supabase's transaction pooler, port 6543), `VITE_SUPABASE_URL` (for the handlers' sign-in) and `UNDERCOVER_API_KEY`. Lambda sets `AWS_LAMBDA_FUNCTION_NAME`, and with it the store opens a connection for each request and keeps none (`NullPool`), prepares no statements (`prepare_threshold=None`), and never makes the schema or tables or seeds; run `npm run seed` against the database first. Everything else the backend reads has a default, or is needed only for runs and evaluations, which need the agent: on its own host at `UNDERCOVER_AGENT`, or on AgentCore Runtime with `UNDERCOVER_AGENT_RUNTIME`.
